# 인증 공통 계약 초안

## 목적과 적용 범위

이 문서는 Android, iOS, Backend가 동일한 로그인 경험을 구현하기 위한 플랫폼
중립 규칙을 정의한다. 실제 API 엔드포인트, 요청·응답 필드, 토큰 형식과 만료 시간은
백엔드 계약이 확정되기 전까지 정의하지 않는다.

결정 상태와 담당자는 [공통 계약 결정 목록](contract-decisions.md), 기존 미정 사항은
[확인 필요 항목](open-questions.md)에서 관리한다.

## 기본 원칙

- **CONFIRMED**: Android와 iOS는 동일한 Spring Boot 백엔드를 사용한다.
- **PROPOSED**: 백엔드의 사용자 식별자를 계정의 유일한 기준으로 사용한다. 기기,
  운영체제 또는 소셜 제공자의 표시 이름을 앱 계정 식별자로 사용하지 않는다.
- **PROPOSED**: 모바일 앱은 제공자 인증 UI와 자격 증명 전달을 담당하고, 백엔드는
  제공자 자격 증명 검증, 사용자 연결, 서비스 세션 발급과 폐기를 담당한다.
- **OPEN**: Apple, Kakao, Google 중 실제 지원 범위와 출시 순서는 제품·Android·iOS·
  Backend가 확정해야 한다. Figma의 버튼은 후보 UI이며 지원 확정의 근거가 아니다.

## 소셜 로그인 제공자별 흐름

지원이 확정된 제공자마다 아래 순서를 공통 흐름으로 사용한다.

1. 앱이 제공자의 공식 SDK 또는 승인된 웹 인증 흐름을 시작한다.
2. 사용자가 취소하면 앱은 로그인 전 상태로 돌아가며 실패로 과장하지 않는다.
3. 앱은 제공자가 발급한 단기 자격 증명을 TLS로 백엔드에 전달한다.
4. 백엔드는 제공자와 자격 증명의 유효성을 검증하고 내부 사용자를 조회하거나,
   허용된 정책에 따라 생성·연결한다.
5. 백엔드 인증이 성공한 경우에만 앱의 로그인 상태를 확정한다.
6. 앱은 서비스 토큰을 안전하게 보관하고 사용자 데이터를 다시 조회한다.

제공자별 SDK, 필요한 credential 종류, nonce/PKCE 사용 여부, 취소·오류 코드 매핑은
각 제공자 정책과 백엔드 계약을 함께 검토해야 하는 **OPEN** 항목이다. 클라이언트는
제공자 credential을 자체 해석해 서비스 사용자로 확정하지 않는다.

## 동일 계정 공유

- **PROPOSED**: 같은 백엔드 사용자 식별자에 연결된 로그인은 Android와 iOS에서
  동일 계정과 동일 서버 데이터를 조회한다.
- **PROPOSED**: 제공자별 외부 식별자와 내부 사용자 간 연결은 백엔드에서만 관리한다.
- **OPEN**: 동일 이메일을 반환하는 서로 다른 제공자를 자동으로 합칠지, 명시적 계정
  연결을 요구할지 Backend와 제품 담당자가 결정해야 한다.
- **OPEN**: Apple의 비공개 이메일, 제공자 이메일 변경, 이미 연결된 계정 충돌을
  처리하는 정책이 필요하다.

이 정책이 확정되기 전에는 계정 연결·해제 UI와 이메일 기반 자동 병합을 구현하지 않는다.

## 서버와 모바일 앱의 역할

| 구분 | 모바일 앱 | Backend |
|---|---|---|
| 제공자 인증 | 공식 인증 화면 시작, 결과 수신, 취소 처리 | 제공자 credential 검증 |
| 서비스 사용자 | 로그인 진행 상태 표시 | 내부 사용자 식별·생성·연결 정책 적용 |
| 서비스 세션 | 토큰 저장, 요청 첨부, 만료 대응 | Access/Refresh Token 발급·검증·회수 |
| 권한 | 화면 접근 제어는 사용자 경험 보조 | 모든 보호 자원 접근을 최종 인가 |
| 비밀정보 | 제공자·백엔드 비밀키를 포함하지 않음 | 비밀키와 서버 자격 증명을 보호 |

## Access Token과 Refresh Token

- **PROPOSED**: Access Token은 API 요청에만 사용하고 로그, 분석 이벤트, 오류 보고,
  URL 또는 일반 설정 저장소에 남기지 않는다.
- **PROPOSED**: Refresh Token은 Android Keystore 기반 보안 저장소와 iOS Keychain처럼
  운영체제가 제공하는 보호 저장소에 저장한다. Access Token도 영속 보관이 필요하다면
  동일 수준으로 보호한다.
- **PROPOSED**: 동시에 여러 요청에서 만료가 감지되더라도 갱신은 한 번만 수행하고,
  대기 요청은 갱신 결과를 공유한다.
- **PROPOSED**: 갱신 성공 후 실패했던 요청은 멱등성과 본문 재전송 가능성을 확인한
  경우에만 한 번 재시도한다.
- **OPEN**: 토큰 형식, 만료 시간, 회전 여부, 재사용 탐지, 다중 기기 세션 정책과
  갱신 요청 계약은 Backend가 확정해야 한다.

## 인증 만료와 실패 처리

| 상황 | 양 플랫폼의 공통 동작(제안) |
|---|---|
| Access Token 만료, Refresh Token 유효 | 사용자 개입 없이 한 번 갱신하고 원래 작업 재개 |
| Refresh Token 만료·회수·거부 | 로컬 세션 제거 후 재로그인이 필요한 상태로 전환 |
| 사용자가 제공자 로그인을 취소 | 오류 경고 대신 로그인 화면 유지 |
| 네트워크 연결 없음·시간 초과 | 계정을 삭제하지 않고 재시도 가능한 안내 제공 |
| 제공자 또는 서버 인증 거부 | 민감한 원문을 노출하지 않고 로그인 실패 안내 |
| 알 수 없는 서버 오류 | 일반 오류와 재시도 경로를 제공하고 토큰을 로그에 남기지 않음 |

오류 코드와 재시도 가능 여부를 전달할 서버 응답 계약은 **OPEN**이다. 계약 확정 전에는
HTTP 상태만으로 계정 삭제나 영구 로그아웃을 추론하지 않는다.

## 로그아웃과 계정 탈퇴

- **PROPOSED**: 로그아웃은 서버 세션 회수를 시도한 뒤 로컬 토큰과 사용자별 캐시를
  제거하고 로그인 화면으로 이동한다.
- **PROPOSED**: 로그아웃 요청이 네트워크 오류로 실패해도 로컬 로그아웃은 완료하되,
  서버 세션 회수 실패를 안전하게 처리할 후속 정책이 필요하다.
- **PROPOSED**: 계정 탈퇴는 로그아웃과 다른 명시적 작업이며 재확인 절차를 둔다.
- **OPEN**: 탈퇴 인증 방식, 유예 기간, 복구 가능 여부, 데이터 삭제 범위와 법적 보존
  항목은 제품·Backend가 결정해야 한다.

탈퇴 계약이 확정되기 전에는 실제 탈퇴 요청과 완료 화면을 구현하지 않는다.

## 공통 사용자 경험

- 지원 제공자, 버튼 순서와 설명은 출시 정책이 확정된 뒤 양 플랫폼에서 동일하게 맞춘다.
- 진행 중 중복 탭을 막고 취소, 네트워크 오류, 인증 거부를 서로 다른 메시지로 표현한다.
- 세션 갱신 중 잠깐 로그인 화면을 노출하지 않는다.
- 재로그인이 필요하면 진행 중 입력의 손실 가능성을 안내하고 가능한 안전한 복구 경로를 둔다.
- 접근성 레이블에는 제공자와 동작을 포함하되 credential이나 사용자 식별자를 포함하지 않는다.

## Backend 검토가 필요한 계약

지원 제공자와 credential 종류, 계정 연결 정책, 토큰 수명·회전·회수, 오류 분류,
다중 기기 세션, 로그아웃 및 탈퇴의 서버 동작이 확정되어야 실제 인증 기능을 구현할 수
있다. 확정 결과는 이 문서와 [공통 계약 결정 목록](contract-decisions.md)에 함께 반영한다.
