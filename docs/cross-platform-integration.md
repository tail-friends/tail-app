# Android·iOS 통합 테스트 체크리스트

## 현재 상태

이 문서는 실제 서버 계약과 양 플랫폼 기능이 준비된 뒤 수행할 통합 테스트 계획이다.
현재 저장소에는 확정된 인증·사육 데이터·캐릭터 API 계약과 양 플랫폼 구현이 없으므로
아래 시나리오는 **미실행**이다. 체크 항목을 작성했다는 사실을 테스트 통과로 간주하지 않는다.

## 공통 사전 조건

- 검토 완료된 Backend API 계약과 테스트 환경이 준비되어야 한다.
- 같은 테스트 사용자와 서로 구분되는 Android/iOS 테스트 기기를 준비한다.
- 서버 시간, 계정/개체 기준 시간대, 체중 단위와 정밀도가 확정되어야 한다.
- 지원 로그인 제공자와 테스트 계정 정책이 확정되어야 한다.
- 로그에 credential, Access/Refresh Token, 개인정보가 남지 않아야 한다.
- 각 단계에서 요청 시각, 앱 버전, 플랫폼, 기대 결과와 실제 결과를 민감정보 없이 기록한다.

## 1. Android 로그인 후 iOS 로그인

- [ ] Android에서 확정된 제공자로 로그인한다.
- [ ] 서버 사용자 식별자를 노출하지 않는 안전한 방법으로 테스트 계정을 확인한다.
- [ ] iOS에서 동일한 제공자 또는 허용된 연결 제공자로 로그인한다.
- [ ] 두 플랫폼이 동일 계정의 서버 데이터를 표시하는지 확인한다.
- [ ] 한 플랫폼 로그인 때문에 다른 플랫폼 세션이 예기치 않게 종료되지 않는지 확인한다.

계정 연결과 다중 기기 정책이 확정되기 전에는 실행을 보류한다.

## 2. Android 등록 후 iOS 조회

- [ ] Android에서 경계값을 포함한 유효한 개체를 등록한다.
- [ ] 저장 성공을 확인한 뒤 iOS에서 동기화한다.
- [ ] 이름, 종, 날짜, 급여 주기와 캐릭터 연결 값이 동일한 의미로 표시되는지 확인한다.
- [ ] 선택 값을 비운 경우 `null`·생략·빈 문자열이 의도대로 유지되는지 확인한다.

## 3. iOS 급여 기록 후 Android 조회

- [ ] iOS에서 정상 급여 기록을 추가한다.
- [ ] Android에서 발생 날짜·시각, 결과와 선택 메모가 동일하게 보이는지 확인한다.
- [ ] 다음 급여일이 마지막 정상 급여일과 급여 주기로 계산되는지 확인한다.
- [ ] 수정과 삭제 후 두 플랫폼의 목록과 파생 상태가 다시 일치하는지 확인한다.

## 4. 급여 거부와 다음 급여일

- [ ] 기존 정상 급여 기록으로 다음 급여일을 확인한다.
- [ ] 한 플랫폼에서 그 이후 날짜의 급여 거부를 기록한다.
- [ ] 양 플랫폼에서 마지막 정상 급여일이 바뀌지 않는지 확인한다.
- [ ] 양 플랫폼의 다음 급여일과 `NO_RECORD`/`UPCOMING`/`DUE`/`OVERDUE` 상태가 일치하는지 확인한다.
- [ ] 급여 거부를 수정·삭제해도 정상 급여 기준이 유지되는지 확인한다.

## 5. Android 캐릭터 수정 후 iOS 표시

- [ ] Android에서 확정된 종·색상·무늬·체형 조합을 저장한다.
- [ ] iOS에서 동일한 속성 code와 시각적 의미가 적용되는지 확인한다.
- [ ] 각 `IDLE`, `WALK`, `CHASE`, `EAT`, `REACT`, `SLEEP` 상태를 재현한다.
- [ ] 상태 전환, 반복, 우선순위와 fallback이 양 플랫폼에서 계약과 일치하는지 확인한다.
- [ ] 알 수 없는 속성 code와 에셋 로딩 실패에서 안전한 대체 표현을 확인한다.

## 6. 토큰 만료와 로그아웃

- [ ] Access Token만 만료시켜 양 플랫폼이 한 번 갱신 후 작업을 재개하는지 확인한다.
- [ ] Refresh Token 만료·회수 상황에서 모두 재로그인 상태로 이동하는지 확인한다.
- [ ] 네트워크 단절 상태에서 로그아웃 후 로컬 토큰과 사용자 캐시가 제거되는지 확인한다.
- [ ] 다중 기기 정책에 따라 한 플랫폼의 로그아웃이 다른 플랫폼에 미치는 영향을 확인한다.
- [ ] 토큰이나 credential이 화면·로그·분석 이벤트에 노출되지 않는지 확인한다.

## 7. 네트워크 오류와 데이터 누락

- [ ] 등록·수정·삭제 각각에서 오프라인, 시간 초과와 서버 오류를 재현한다.
- [ ] 실패 작업을 성공으로 표시하지 않고 입력 또는 복구 가능한 상태를 유지하는지 확인한다.
- [ ] 필수 필드 누락, 알 수 없는 enum과 부분 캐릭터 데이터를 주입한다.
- [ ] 양 플랫폼이 크래시하지 않고 동일한 오류 범주와 재시도 경로를 제공하는지 확인한다.
- [ ] 재시도로 중복 기록이 생성되지 않는지 확인한다.

## 8. 날짜·시간·체중 단위

- [ ] 같은 timestamp를 서로 다른 기기 시간대에서 조회해 계약된 현지화 결과를 확인한다.
- [ ] 자정 전후와 일광절약시간 전환이 있는 시간대에서 급여 상태 경계를 확인한다.
- [ ] 날짜 전용 값이 시간대 변환으로 전날·다음 날이 되지 않는지 확인한다.
- [ ] 같은 체중을 양 플랫폼에서 입력·조회·수정해 값과 단위가 보존되는지 확인한다.
- [ ] 허용 소수 자릿수와 반올림 경계에서 결과가 일치하는지 확인한다.

## 결과 기록 기준

각 시나리오는 `PASS`, `FAIL`, `BLOCKED` 중 하나와 실행 환경, 서버 계약 버전, 증거,
차이를 기록한다. 서버 미연결, 계약 미확정 또는 한 플랫폼 미구현은 `PASS`가 아니라
`BLOCKED` 또는 `미실행`으로 남긴다. 차이가 발견되면 어느 플랫폼이 맞는지 추측하지
말고 [공통 계약 결정 목록](contract-decisions.md)의 해당 결정부터 확정한다.
